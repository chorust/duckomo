# Open-Meteo projected-sample axis order

Date: 2026-10-08  
Question: Can the OM-array axes for the rotated GEM, stereographic GEM, and Lambert samples be mapped to Open-Meteo producer point order from pinned primary sources and the OM objects, without converting GRIB or other data?

## Finding

The pinned Open-Meteo source defines producer grid-point order exactly: for producer point `p`, `y = p / nx`, `x = p % nx`, so `p = y * nx + x` and x/column varies fastest. The pinned `open-data` README defines rolling `data/` arrays as `[ny,nx,ntime]`. The pinned producer's writers and rolling-time-series conversion code use those dimensions and pass each spatial row/column slice through without a spatial transpose. Each fixed OM sample has root dimensions matching its source grid's `[ny,nx]` and its manifest records that OM array metadata does not embed axis names.

Therefore, **under the published Open-Meteo `data/` layout contract**, the source-derived mapping is axis 0 = producer y/row, axis 1 = producer x/column, and axis 2 = time. This can be documented without converting GRIB. For an array shape `[ny,nx,ntime]`, the OM logical position for producer point `p` and time `t` is `(p * ntime) + t`.

This is a producer-contract mapping, not an independent, per-object proof that every value in these exact S3 objects is in that order. The OM arrays have no semantic axis labels, and the fixed object metadata does not identify the producer source revision. Keep any gate requiring object-specific independent axis/value confirmation as not-run until that distinct check is performed.

## Primary-source basis

1. **Producer point order.** In the pinned [`ProjectionGrid.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Domains/ProjectionGrid.swift#L59-L94), `findPoint` returns `y * nx + x`; `getCoordinates` reverses that mapping with integer division and remainder, then derives projected coordinates from x and y. This establishes Open-Meteo's flattened point order independently of OM metadata.
2. **The three source grids.** The pinned [`GemDomain.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Gem/GemDomain.swift#L248-L270) declares the stereographic GEM grid as `nx=935, ny=824` and rotated GEM as `nx=1140, ny=1045`. The pinned [`ChmiDomain.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Chmi/ChmiDomain.swift#L62-L73) declares Lambert ALADIN as `nx=1053, ny=837` and identifies the grid as Lambert Conformal Conic. These are grid row/column dimensions; for the projected grids, they should not be mistaken for geographic latitude/longitude coordinates.
3. **Published array layout.** The pinned [`open-data` README](https://github.com/open-meteo/open-data/blob/4fd52ad16c417c49bff45fab4bf175e5ea5760f2/README.md#L118-L147) states that rolling `data/` arrays use `[ny,nx,ntime]`; spatial files use `[ny,nx]`. The README describes dimension names/order, not per-object coordinate variables.
4. **Producer writes spatial arrays in grid dimensions.** The pinned [`GemDownloader.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Gem/GemDownloader.swift#L227-L268) calls `to2D(nx:domain.grid.nx, ny:domain.grid.ny, ...)`, performs a 180-degree shift only for the global GEM cases (not the two sampled regional GEM domains), and passes `grib2d.array.data` to the writer. [`OmSpatialTimestepWriter.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Helper/OmSpatialTimestepWriter.swift#L104-L128) prepares dimensions `[ny,nx]` and writes the data array directly. For CHMI, [`ChmiDownloader.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Chmi/ChmiDownloader.swift#L187-L233) copies each decoded spatial index unchanged into a time-major buffer, then passes each time slice to the same spatial writer.
5. **Rolling `data/` conversion preserves y/x ranges.** [`GenericVariableHandle.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Helper/Writer/GenericVariableHandle.swift#L18-L28) checks incoming spatial array dimensions against `ny,nx`. Its rolling conversion reads `[yRange,xRange,time]` and carries the corresponding contiguous location slice into its output buffer ([lines 380–421](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Helper/Writer/GenericVariableHandle.swift#L380-L421)). [`OmFileSplitter.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Helper/OmFileSplitter.swift#L385-L471) writes `[ny,nx,ntime]` (or the corresponding member-extended form) with matching `[yRange,xRange,time]` blocks. Together with the README convention, this documents the producer's intended `data/` layout.
6. **The GRIB path is source-visible, but no conversion was run here.** The pinned Open-Meteo [`Package.resolved`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Package.resolved#L310-L316) pins SwiftEccodes revision `98b77f84a2f5a890eb9a7d0c584174decfd66ce7`. Open-Meteo's [`Curl+Grib.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Helper/Download/Curl%2BGrib.swift#L129-L182) copies the ecCodes `values` array sequentially into its `Array2D`; its [`DebugFromGRIB.swift`](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Domains/DebugFromGRIB.swift#L41-L48) diagnostic enumerates GRIB coordinates as `x=i%nx, y=i/nx` and compares them to `grid.findPoint` ([lines 74–93](https://github.com/open-meteo/open-meteo/blob/b06f4760fd1f997e5559bb380f64c5e496b4a509/Sources/App/Domains/DebugFromGRIB.swift#L74-L93)). The diagnostic's existence describes how Open-Meteo can check GRIB ordering; it is not evidence that it was run successfully on the source GRIB for these S3 objects.

## What this does and does not establish

- **Established from pinned source:** Open-Meteo maps producer integer point `p` to row `y=floor(p/nx)` and column `x=p mod nx`; its documented and implemented rolling-array convention is `[ny,nx,ntime]`. The intended object axis mapping is therefore row/column/time for these samples.
- **Consistent with each pinned object:** The actual shape in each hash-pinned OM file matches the pinned source grid dimensions and the Open-Meteo `[ny,nx,ntime]` schema. Shape distinguishes the two spatial dimension lengths in these examples, but shape alone does not establish the meaning or value order of those dimensions.
- **Not independently established for these exact object bytes:** The root arrays carry no semantic axis labels or coordinate arrays, and there is no object-level producer commit identifier. A source-code path and matching shape establish the declared producer contract, not that these historical/public bytes were produced by this exact commit or that no intervening publication path changed the point order. The official OM C value references in the manifest are indexed by zero-based OM linear position; they do not attach geographic coordinates to those positions.
- **No GRIB conversion was performed.** The references above inspect pinned source and existing OM metadata/manifests only. A stronger sample-specific proof still requires a coordinate/value pair tied to the same OM indices, or an equivalent direct cross-check against a producer-generated spatial object/reference with matching time and source identity. Converting GRIB is one possible way to make such a reference, but is not required to state the producer contract.

## Implementation/evidence implication

Use `y`/row and `x`/column terminology for the two spatial axes in projected grids. The existing manifest's `axes: ["latitude", "longitude", "time"]` is not embedded OM metadata and overstates what the projected axes are named by the file. The source-derived `[y,x,time]` mapping can be recorded as the expected Open-Meteo layout; retain the independent object-axis mapping / H1 gate as not-run if its acceptance requires validation against the actual OM sample values.
